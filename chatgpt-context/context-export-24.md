## Multi-agent / GitHub coordination — дополнительные правила пользователя

### 2026-08-21 — coordination protocol
В долговременной памяти сохранена архитектура координации нескольких AI-агентов через GitHub:
- сообщения между агентами хранятся как отдельные immutable `.md` files;
- `coordination/state.json` хранит активного исполнителя/ход;
- GitHub Actions валидирует handoff;
- `next_actor` является авторитетным указателем того, кто должен действовать дальше.

Пользователь отдельно требовал, чтобы агент проверял `coordination/state.json` максимально часто, особенно:
- перед операцией;
- после операции;
- перед/после commit;
- перед/после generation;
- после изменения log/state;
- перед переходом в ожидание.

Это не общая рекомендация, а установленное правило конкретного multi-agent workflow.

### 2026-08-21 — экспорт контекста для Grok
Для одной из миграций/обучающих веток пользователь установил жёсткие ограничения:
- работать только в ветке `grok-training-context-2026-08-22`;
- не трогать `main`;
- не трогать `-alisa-instagram`, если нет реального пробела в canon;
- сначала читать первичные файлы;
- факты только из памяти маркировать `memory_unverified`;
- не переносить нерелевантные личные/чувствительные сведения.

Для второго прохода пользователь дополнительно требовал:
- не дублировать уже выгруженные блоки 12–19;
- держать неподтверждённые факты отдельно;
- принцип `one fact / one source`;
- сохранять конфликты, а не сглаживать их;
- не выводить цены, пороги, юридические суммы, Ozon economics или факт подписания документа без первичного источника;
- писать кратким рабочим русским языком.

Это сильный общий сигнал о предпочтении пользователя: provenance и статус факта важнее красивой цельной истории.

### 2026-08-22 — архитектурное решение по агентам
В сохранённой памяти зафиксировано принятое решение:
- не использовать OpenAI API в этой схеме из-за отдельной стоимости;
- ориентироваться на subscription products + GitHub mailbox;
- broker должен быть единственным писателем `state.json` и canonical messages.

Причина: избежать конфликтов записи и сохранить единый authoritative state.

## Общий вывод для Claude/другой LLM
При работе с GitHub-проектами Романа следует различать:
1. canonical source в репозитории;
2. текущий `state.json` / protocol;
3. историческую память модели;
4. assistant-derived предложения.

Если GitHub назначен source of truth, историческая память не должна переопределять состояние репозитория.
